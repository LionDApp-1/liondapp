# LionDApp 活动帖与悬赏任务改版

2026-10-04。依据所有者新增需求：开发者发帖推荐自己的 dApp、邀请测试、自定义人数/提交要求/SKR 奖励；其他用户可组织 X 点赞或关注等任务；平台抽成 10%。本文为已接受的产品规格；免费邀请与奖励草稿已实现，真实托管或付款尚未开放。最新状态见 [project-status.md](project-status.md)。旧开发预算不会被解释为已预存的奖励。

## 产品主线

LionDApp 为 Seeker 用户提供发现应用、参加测试或推广活动、提交成果并获得奖励的入口；为发起者提供活动发布、招募、反馈归集与验收入口。现有体验评价保留为长期有用的内容。活动结束后，负面体验、问题和改进建议仍能被开发者找到。

免费活动与付费任务共用活动帖。关联官方目录应用、介绍、媒体、作者、截止时间、评论和招募入口构成帖子；付费任务额外具有明确的奖励规则、名额、完成证明、审核与结算状态。

## 三种活动

| 类型 | 参与者提交 | 发起者获得 | 奖励 |
| --- | --- | --- | --- |
| 推荐 / 免费试用 | 使用体验或普通讨论 | 曝光、交流、愿意测试的用户 | 无奖励承诺 |
| 悬赏测试 | 规定测试步骤的结果、问题或体验，可附证据 | 可验收的测试报告 | 达标后按任务规则结算 |
| 推广任务 | 指定链接对应的完成证明 | 已声明为付费激励的推广参与 | 达标后按任务规则结算 |

所有者已确认第一版先完成 dApp 测试悬赏，X 点赞 / 关注留待后续。上线 X 任务需要对应官方接口、账号绑定、完成证明和第三方平台规则核查。截图或点击外链不等同于已验证点赞 / 关注。

评论区按所有者提供的参考采用底部评论面板，作为日常交流入口。悬赏成果通过单独的“提交测试结果”入口提交，携带任务 ID、报名记录与要求检查，避免把任意普通评论都算作可领赏结果。

## 活动帖与页面区域

- 发现：推荐应用与有价值的真实反馈；活动：筛选测试 / 推广、奖励、剩余名额与截止时间；我的：我参加的、我发起的、奖励结算记录。
- 帖子阅读区：作者、关联 dApp / 目标链接、标题、图片 / 演示、介绍。
- 任务区：参与者实际到手奖励、可领取名额、要求、截止时间、报名 / 提交入口。免费活动没有虚构赏金数额。
- 进展区：已报名、待验收、已通过、已结算分开显示。“提交”与“获得奖励”不使用同一个状态。
- 讨论区：灰色底部评论面板、头像、用户名、正文、日期、回复与点赞、折叠回复；保留公开讨论，不与验收表混合。
- 发起者管理：参与名单、成果、通过 / 退回补充 / 拒绝及原因、待结算金额、费用与可退余额。

## 发布与验收规则

1. 选择活动类型；测试活动必须关联具体 dApp 与版本，推广活动必须提供目标链接和具体动作。
2. 输入人数上限、每人的到手奖励、报名与提交截止时间。
3. 输入完成步骤、必要证明、提交长度与验收标准。第一版用有限的条件控件，避免只有一段不可执行的自由文本规则。
4. “100 字以上”是可配置的最低有效字符数：空白不计入，并显示计数；英文单词数另作可选指标，不把 100 个英文单词和 100 个字符混为一谈。
5. 有效测试应覆盖任务要求，重复、无关、只堆字数的提交可退回或拒绝。发现问题或给出负面评价也能符合条件；不能以好评作为测试领奖条件。
6. 发布前显示全部规则与费用。活动发布/预存后锁定奖励、人数及验收条件；重大修改创建新活动，不能修改已有参与者的交易条件。
7. 投稿人名额与钱包 / 平台身份唯一；同一活动同一身份不能重复领赏。`.skr` 登录不表示绝对防刷或真人证明。
8. 报名预占名额，设定提交时限，超时释放；等待验收的占用不能直接被新参与者顶替。领取窗口与最长审核时限在发布前明确。
9. 发起者验收必须逐项对照公开标准，拒绝填写理由。支持一次补充与平台复核；争议部分的奖励保留至结案。审核超时进入复核队列，不能由发起者无限拖延或取消后取走已承诺部分。

## 10% 费用计算

每人显示的奖励是净到手金额；平台费由发起者另付，按已成功结算奖励的 10% 收取，不从参与者的标示奖励扣减。

| 100 人、每人 10 SKR | 金额 |
| --- | --- |
| 参与者奖励池 | 1,000 SKR |
| 最大平台费 | 100 SKR |
| 发布前需预存 | 1,100 SKR |
| 若最终仅 60 人验收并成功结算 | 600 SKR 奖励 + 60 SKR 平台费 |
| 无其他未决申领时可退款 | 440 SKR |

网络费另行显示。SPL Token 使用最小单位整数计算；每名额手续费按 10% 向上取整至最小单位。退款只释放未占用且无待验收 / 争议的额度。未发出的奖励对应手续费随余额退回。发起者不能发布没有资金覆盖的付费活动。

## 已确认的资金方式

所有者已选择先预存全部奖励及费用，验收后结算。采用链上程序管理托管账户，可验证奖池，不让用户把活动资金发送到平台打赏地址；平台后台不保管用户私钥。现有钱包登录与打赏代码不能替代托管。

若选择发起者自行付款，页面需显示“发起者自行付款”，平台只能追踪付款凭据；不能保证资金覆盖、自动退款或 10% 必然收取。这与推荐的预存流程是不同的交付范围。

## 状态与记录

活动状态：草稿 → 待资金确认 → 开放报名 → 停止报名 / 等待验收 → 结算中 → 完成。取消与余额退回单独记录。

参与状态：已报名 → 已提交 → 待验收 → 需补充 / 已通过 / 已拒绝 / 争议中 → 待结算 → 链上已结算。取消报名、超时、失败重试有明确状态。

最少记录：活动、锁定规则版本、报名、成果及修订、验收记录、复核记录、资金入账、每笔支付与平台费、退款。支付记录绑定活动 / 成果 / 收款钱包与链上签名，同一成果只能成功结算一次。链上交易成功确认后才显示“已获得奖励”。

验收通知应能返回具体任务和成果；活动评论、点赞、关注继续是普通社区功能，不代表成果验收通过。

## 实施顺序

1. 明确资金方式、第一版任务范围和 10% 费用口径。免费推荐与招募可沿用现有帖子、目录关联和讨论能力。
2. 建立活动与成果模型，完成报名名额控制、提交要求、管理验收、复核和通知；用隔离数据验证整个流程。
3. 实现 SKR 资金模块：奖池资金确认、锁定额度、幂等付款、平台费、余额退款与链上核对；在开发网络验证并保持主网关闭。
4. 真机测试报名冲突、重复领取、修改规则、审核超时、争议、付款失败、链上已成功但网络响应丢失、退款与待验收额度并存。
5. 完成真实资金验证后开放主网。X 子类型在证明能力成立后开放；不以模拟接口冒充真实验证。
